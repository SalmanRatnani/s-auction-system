# S Auction System — code and logic audit (2026-10-19)

## Scope / limitations
Static source review of Next.js routes, core auction RPC migrations, Supabase RLS, role/access flows, webhook, auction UI, purse ledger and viewer links. This is **not** proof of a fully functioning production system: no Supabase production credentials were used, and local clone/build was unavailable due to DNS restrictions. Confirm live DB migration state before applying changes.

## Critical — fix before running a live auction

1. **Self-upgrade to controller role** (`supabase/migrations/0002_rls.sql`): `users_self_update` allows self UPDATE without restricting `role`. If authenticated users have UPDATE privilege (typical Supabase public-table grants), a user can mutate their own role. The `sync_role_to_jwt` trigger in 0006 then propagates this into app metadata. Remove general self UPDATE; allow profile edits only with a column-scoped grant or trusted server endpoint.
2. **Viewer tokens visible to others** (`0002_rls.sql`): `viewer_links` has `FOR SELECT USING (true)`, disclosing access tokens. Restrict tokens to controllers; validate in server-side watch routes.
3. **Unauthorized audit log injection** (`0002_rls.sql`): `audit_insert FOR INSERT WITH CHECK(true)` allows arbitrary inserts by callers granted INSERT. Audit entries should only be written from trusted server methods or narrowly permissioned functions.
4. **Sensitive player data exposure**: `players_read_captains_viewers` permits authenticated reads on all `players` rows. Base table contains DOB, age proof URLs and other sensitive registration information. Only expose columns through a security-invoker safe view or column privileges.
5. **Age-proof storage write unrestricted** (`0004_storage.sql`): `age_proofs_staff_write` checks bucket only; any caller with the insert privilege can upload to the private bucket. Verify auth and staff/controller role.

## High — auction correctness

6. **Bid amount server validation missing** (`0014_block_captain_bids.sql`): validates only `p_amount > current highest`; does not enforce per-grade base price or increment. Clients can send an arbitrarily small positive bid below base price or increments.
7. **Bids allowed while PAUSED / DRAFT / ENDED**: current `place_bid` checks auction-player status CURRENT, but not `auctions.status = LIVE`. Pausing/end does not clear CURRENT, so captains can still bid by calling RPC directly.
8. **Squad limit hard-coded to 18**: SQL ignores configured `maxSquad`. Purses are checked only against current ledger; reserve guards/config options also not enforced server-side.
9. **Direct table writes bypass business logic**: `auction_players`, `team_players`, `purse_ledger` have write RLS policies for staff/controller. RLS does not enforce one player CURRENT or money / category constraints for these direct writes. Use narrow RPCs and revoke client writes.
10. **Nonatomic mutations**: `assign-captain`, `reset`, `unsold`, `round2`, `start`, registration approval and several other API routes run separate service-role SQL requests. Midway failure may leave inconsistent roster/ledger/player state. Move coupled writes into one SQL transaction/SECURITY DEFINER RPC and add guarded transitions.
11. **Draw race condition** (`next-player/route.ts`): checks no CURRENT and then chooses/updates PENDING in separate requests. Two concurrent requests can draw two players. Use single DB-transaction draw and partial unique index on `auction_players(auction_id) WHERE status = 'CURRENT'`.
12. **Round 2 isn't round 2**: `round2/route.ts` changes UNSOLD rows back to PENDING without increasing `round` or inserting round=2 rows. `sell_player` will consequently classify a second-round sale as `BID` instead of `ROUND2`.
13. **Cross-auction integrity gaps**: foreign keys link team and player tables independently but do not always constrain them to the same auction; triggers or composite FKs may be needed.
14. **Finished auctions restart incorrectly**: `start/route.ts` accepts ENDED and reseeds rows, but records can remain SOLD. Enforce DRAFT -> LIVE only, or implement a clearly defined restart.
15. **Manual playing-captain price varies with draw order**: captain assignment averages *currently sold* matching category. If captain drawn early, falls back to base price. If category average is a business rule, defer final valuation or establish a locked baseline. Ensure assignment is one transaction.
16. **Incorrect/ambiguous permission toggles**: `showPurseToCaptains`, `showPurseToViewers`, timer and reserveGuard appear in config UI but are not consistently enforced by data endpoints. Public state endpoint returns auction configuration and team data through a service-role client; confirm intended visibility.
17. **Unscoped public state endpoint** (`state/route.ts`): fetches auction by guessed UUID without viewer-link access check. It exposes bidding, current player, teams and counts for any auction ID. Use explicit spectator token or published/public auction state.
18. **Public viewer access token lifetime**: initial server page checks token expiry, but client polls state API with auction ID only; access is not rechecked after token expiry.
19. **Viewer token generation** (`src/lib/utils.ts`): uses `Math.random()` rather than cryptographically secure randomness. Use `crypto.randomBytes` or `crypto.randomUUID`.
20. **Registration approval duplicates/code collisions**: player code generated from count+1 can collide after deletes or concurrent approvals; registration lookup and insert aren't one transaction; there is no unique constraint on `players.registration_id`.
21. **Deletion while live auction**: `players/[id]/route.ts` blocks CURRENT only but can delete a PENDING/UNSOLD player during an active auction, altering queue and destroying bid history.
22. **Purse adjustments accept invalid numbers**: `topup/route.ts` checks truthiness but not integer, finite, bound or safe value. Inconsistent amounts may hit a bigint column; define an explicit paise integer contract and maximum.
23. **Audit failures ignored**: many mutating routes respond success even if the audit insert fails. For high-impact events, include audit writes in the same DB transaction.

## Medium — maintenance/performance

24. **Frequent polling plus 6 realtime subscriptions** (`useAuctionState`): every captain polls at 1.5s, viewers at 2.5s, while listening on 6 tables. With enough viewers, `state/route.ts` fires multiple administrative DB queries for each poll. Consider broadcast/single denormalized read endpoint, throttled fan-out, and stale response cancellation.
25. **Repeated role verification boilerplate**: centralize server-side `requireRole` helpers. Never trust client UI to enforce permissions.
26. **Config duplication and drift**: `src/constants/auction-config.ts`, admin `AuctionConfig`, `categories.ts` and SQL disagree about default squad size, increments and auction policies. One validated schema should be used in API and DB.
27. **CSV formula injection**: user-supplied names/team names beginning with =, +, - or @ may execute when opened in spreadsheet software. Escape formula-triggering prefixes.
28. **Webhook/upload input hardening**: cap request size, validate object shape and file MIME/size; normalize untrusted `responseId` so storage paths cannot contain arbitrary slashes.
29. **Unused / legacy implementation**: `increment` config is visibly labelled unused; `src/constants/auction-config.ts` duplicates admin defaults; `randomToken` should be replaced by a secure generator. Search import graph before removing.
30. **Currency display**: database units are paise, but demo display uses rupee-like numeric values. Demo is illustrative and not connected to auction RPC; ensure users cannot mistake it for live bidding.

## Recommended phased plan

### Phase 0 — before SQL changes
- Back up Supabase DB + storage and confirm active migration history.
- Check for users with unexpected MAIN_CONTROLLER role; rotate/revoke leaked viewer links as appropriate.
- Stage DB changes in a non-production Supabase project first.

### Phase 1 — security
- Remove `users_self_update` and overly broad viewer/audit/player access.
- Constrain storage upload policies and direct table writes.
- Introduce privileged immutable audit writing.
- Validate token access on every spectator API request.

### Phase 2 — transactional consistency
- Move bid, draw, sell, unsold, assignment, requeue and reset into transaction-safe database functions with locks.
- Enforce per-category base/increment, auction LIVE status, max squad, minimum purse reserves and category ownership *inside SQL*.
- Add constraints/indexes for one CURRENT row, one player-grade per team, unique registration approval and auction consistency.

### Phase 3 — testing and cleanup
- Add automated integration tests for role spoofing, token expiry, concurrent bids/draws, pause during bid, undo, failed sale rollback, purse boundaries, double approval, reset and round 2.
- Remove dead configs only after confirming no existing DB consumers need them.
- Run `npx tsc --noEmit` and `npm run build` with configured Supabase environment on CI and Vercel preview.

**Deployment:** Do not merge data-layer changes or run SQL migrations directly on production without staging tests and database backups.
